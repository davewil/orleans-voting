  Key Architectural Changes

  1. OrleansVoting.Contracts (Class Library)

  Pure interfaces and data contracts - no implementation.

  Purpose:
  - Shared by ALL projects (silos and clients)
  - Defines the "API surface" of your grains
  - Can be versioned independently
  - Published as NuGet package in real production

  Contains:
  - Grain interfaces (IPollGrain, IUserAgentGrain, etc.)
  - DTOs with [GenerateSerializer] attributes
  - Observer interfaces (IPollWatcher)
  - Shared exceptions
  - No dependencies on Orleans hosting, just Microsoft.Orleans.Sdk

  Benefits:
  - Multiple client types can reference without pulling in implementations
  - Clear versioning boundary
  - Can generate OpenAPI specs from contracts
  - Supports Orleans' "interface-based" RPC model

  ---
  2. OrleansVoting.Grains (Class Library)

  Contains only grain implementations.

  Purpose:
  - Business logic lives here
  - Referenced ONLY by silo hosts
  - Never referenced by client applications

  Dependencies:
  - References OrleansVoting.Contracts
  - Microsoft.Orleans.Runtime
  - Microsoft.Orleans.Core.Abstractions

  Benefits:
  - Implementation details hidden from clients
  - Can refactor internals without affecting clients
  - Easier to unit test in isolation
  - Can use internal visibility for helpers

  Aspire Orchestration Changes

  OrleansVoting.AppHost/Program.cs:
  var builder = DistributedApplication.CreateBuilder(args);

  var redis = builder.AddRedis("voting-redis")
      .WithDataVolume();  // Persist data

  var orleans = builder.AddOrleans("voting-cluster")
      .WithClustering(redis)
      .WithGrainStorage("votes", redis);

  // Dedicated silo tier - compute/grain hosting
  var silo = builder.AddProject<Projects.OrleansVoting_Silo>("voting-silo")

      .WithReplicas(5);  // Scale for grain workload

  // Web frontend tier - HTTP traffic
  var web = builder.AddProject<Projects.OrleansVoting_WebApp>("voting-web")
      .WithReference(orleans)  // Client connection
      .WaitFor(silo)  // Wait for at least one silo
      .WithExternalHttpEndpoints()

  // Optional API tier
  var api = builder.AddProject<Projects.OrleansVoting_Api>("voting-api")

  Benefits of This Architecture

  Scalability

  - Scale silos (compute) independently from web (HTTP)
  - Add more silos for complex grain operations
  - Add more web replicas for traffic spikes
  - Different resource allocations per tier

  Deployment

  - Deploy UI changes without touching grain code
  - Deploy grain logic updates without UI downtime
  - Independent versioning strategies
  - Canary deployments per tier

  Development

  - Teams can work independently (UI team vs. domain logic team)
  - Grain developers don't need to run web stack
  - Web developers work against stable grain contracts
  - Easier onboarding (smaller scope per project)

  Testing

  - Unit test grains without any web dependencies
  - Integration test silos in isolation
  - UI tests can use test cluster or mocked grain factory
  - Contract testing between layers

  Reusability

  - Multiple client types share same grain cluster
  - Mobile backend, webhooks, batch jobs all use same grains
  - Grain contracts become your "domain API"

  Security

  - Grain implementations not exposed to web tier
  - Web tier can't accidentally reference internal grain code
  - Clearer trust boundaries
  - Easier to audit what's public vs. internal

  ---
  Migration Path from Current Sample

  1. Create Contracts project → Move interfaces + DTOs
  2. Create Grains project → Move implementations, reference Contracts
  3. Split Service → Create Silo project with Orleans hosting only
  4. Convert Service → Rename to WebApp, remove grain implementations, add Orleans client config
  5. Update AppHost → Add separate silo and web projects with proper references
  6. Update tests → Separate grain tests from UI tests

  ---
  This architecture aligns with microservices principles while leveraging Orleans' actor model and Aspire's orchestration. It's how you'd build a
  production system that needs to scale, evolve, and support multiple client types.

  - Hosts grain activations
  - No public HTTP endpoints
  - Scales independently for computation

  **OrleansVoting.WebApp** - Blazor frontend (Orleans client)
  - Presentation tier
  - Connects to Orleans cluster as client
  - No grain implementations
  - Scales independently for HTTP traffic

  **OrleansVoting.ServiceDefaults** - Shared Aspire configuration
  - OpenTelemetry with Orleans instrumentation
  - Health checks and service discovery

  **OrleansVoting.AppHost** - Aspire orchestration
  - Configures separate silo and web tiers
  - Redis for clustering and persistence
